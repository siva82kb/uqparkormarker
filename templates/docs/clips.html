Words used here

  • Video: one recorded file. A participant has about 180 to 200 of them. Each is either a task video (one task being performed) or an unlabelled video (the time between two tasks).
  • Frame: one picture in a video. The camera takes 30 per second.
  • Timestamp: the clock time saved with each frame.
  • Clip: a {{ clip_seconds }} s piece cut out of a video, {{ clip_frames }} frames long. A clip is what the rater sees and labels.

Where the files are

The app works with three folders. It only reads the recordings in the first. It makes everything in the second. It shares finished work through the third. Pxx stands for the participant's folder name.

1. The source folder: the recordings, on the study's storage drive. Never changed by the app.

<source>/Pxx/Video/
    experiment_details.json            which task each video shows
    task_001_1669336000000000.avi      a task video: the pictures
    task_001_1669336000000000.vidt     its timestamps, one per frame
    unlabelled_x_1669336050000000.avi  an unlabelled video (between two tasks)
    unlabelled_x_1669336050000000.vidt its timestamps
    ...                                about 180 to 200 pairs like these

Every video is a pair of files with the same name. The .avi file holds the pictures. The .vidt file holds one timestamp for each frame of that video. The long number in the name is the time the video started.

2. The output folder: everything the app makes, on this computer, inside the app's own folder.

data4annotation/Pxx/
    recording.json.gz                  step 1: what was read from the source folder
    segments.csv                       step 3: the list of picked clips
    design.toml                        step 3: a copy of study.toml as it was then
    clips/seg_0001.mp4 ...             step 4: the clips, one file each
    generation_time.json               step 4: how long the cutting has taken
    Pxx_<rater>_annotations.csv        the labels, one file per rater

3. The shared folder: on the study's storage drive, for passing clips and labels between raters. Its name ({{ study.share.folder }}) is set in study.toml.

<study folder>/{{ study.share.folder }}/
    clips/Pxx/Pxx_clips.zip            the clips, zipped, for other raters
    clips/Pxx/Pxx_clips_id.txt         which set of clips the zip holds
    ratings/Pxx_<rater>_annotations_<date>-<time>.csv
                                       a rater's labels, once all clips are labelled

The zip holds the clips, segments.csv, design.toml and recording.json.gz. It never holds a label file. A rater who downloads it does not need the source folder.

The settings are in two files beside the app: study.toml (the study design, the same for every rater) and local.toml (this computer: where the source folder is, which participant, and the rater's name).

Four steps

  1. Read. For each video of the participant, the app reads three things from the source folder:
    • the timestamp of every frame, from the video's .vidt file;
    • the number of frames and the frame rate, from the first part of its .avi file (the pictures are not read);
    • the task it shows, from experiment_details.json.
    It saves all of this in recording.json.gz, so the source folder is read only once.
  2. Remove. Using those timestamps, it works out every clip that could be cut from every video, and removes the ones whose timestamps cannot be trusted. The rule has its own page. Nothing is written in this step.
  3. Pick. From the clips that are left, it picks {{ n_clips }} at random, with no two sharing a frame{% if n_task_clips is not none %}: {{ n_task_clips }} from task video and {{ n_unlabelled_clips }} from unlabelled video{% endif %}. The list is written to segments.csv, one row per clip, saying exactly which video and which frames. A copy of study.toml is saved beside it as design.toml.
  4. Cut. For each row of segments.csv, it opens that video's .avi file in the source folder, cuts out the frames, and saves them as a small MP4 file in clips/, named after the row (seg_0001.mp4, seg_0002.mp4, ...).

A clip never crosses from one video into the next.

The number of clips ({{ n_clips }}), the length of a clip ({{ clip_seconds }} s) and the other design choices are read from study.toml. This page shows the values now in that file.

How the clips are picked

{% if n_task_clips is not none %}

The possible clips that were kept go into two lists: one for clips from task videos, one for clips from unlabelled videos. The app picks {{ n_task_clips }} from the task list and {{ n_unlabelled_clips }} from the unlabelled list, which is {{ task_percent }}% from task video. Within each list, every clip has the same chance. A long video has more clips in its list than a short one, so it supplies more, in proportion to its length.

The share is set on purpose. Task video is a small part of the recording, so picking from everything together would give mostly clips from between the tasks. If one list is too short to supply its number, fewer clips are made; the other list does not make up the difference. The data summary says when that happens.

{% else %}

Every possible clip that was kept goes into one list, from all videos together. The app picks from that list at random, and every clip in the list has the same chance. A long video has more clips in the list than a short one, so it supplies more, in proportion to its length.

{% endif %}
  • If a picked clip shares any frame with one already picked, it is thrown back and another is drawn. So no two clips overlap.
  • A clip can start at any frame, not only on whole seconds. One clip might run from 3.2 s to 4.2 s into a video.
  • The picking uses a fixed random seed, so every rater gets exactly the same clips for a participant.

Why a clip is picked, and not a moment in time

Another way would be to pick a random moment during the recording and start the clip at the next frame after it. That is unfair when timestamps have gaps.

Think of buses. If buses come every 10 minutes and you arrive at a random time, you are equally likely to catch any of them.

But if one bus is 3 hours late, nearly everyone who arrives in those 3 hours gets on that one bus. In the same way, the frame just after a 3-second gap would be picked about 90 times more often than a normal frame.

Picking directly from the list avoids this: each clip is in the list once.

What is saved for each clip

Each clip is a row in segments.csv.

ColumnMeaning
segment_idThe clip's name, for example seg_0042. The clip file is clips/seg_0042.mp4.
video_fileThe video it was cut from.
start_frame, end_frameIts first and last frame in that video, counting from 0.
start_time, end_timeThe timestamps of those two frames, in local time.
taskThe task being recorded. Empty for unlabelled video.

end_time is about {{ '%.2f' | format((clip_frames - 1) / 30) }} s after start_time, not {{ clip_seconds }} s, because {{ clip_frames }} frames have {{ clip_frames - 1 }} steps between them.

The frame numbers are exact. They are the surest record of where a clip came from.

What is saved for each label

Each rater has one file, <subject>_<rater>_annotations.csv. A row is added every time the rater labels a clip.

ColumnMeaning
segment_idThe clip that was labelled.
labelThe label given, in words.
raterThe rater's name.
annotated_atWhen the label was given, in local time.

A rater can go back and label a clip again. That adds a new row; the old row stays. The last row for a clip is the one that counts.

Every rater sees the same clips, but in a different shuffled order. The rater does not see which task or video a clip came from.
